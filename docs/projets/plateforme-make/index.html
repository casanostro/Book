CASE 02 En production Point aveugle traité

159 flows, mais combien de flows fiables ?

DomaineAutomatisation métier
RôleAdministration, diagnostic
StackMake, API, Python
StatutPlan de reprise livré

159 scénarios en production, 6 domaines métier, et une migration d'API qui fait échouer des milliers d'exécutions sans un bruit. 159 automatisations ne veulent pas dire 159 automatisations fiables.

Investigation

De la file d'échecs au plan d'action

01 · Le parc

Ce qui tourne tous les jours

159 scénarios couvrant gestes commerciaux, alertes qualité, base des manquants et autres flux du quotidien des équipes. Un parc vivant, connecté à plusieurs SI par webhooks et API.

02 · La rupture

Une migration d'API, des milliers d'échecs

Une rupture de compatibilité côté API fait échouer les exécutions sans déclencher d'alerte. Les échecs s'accumulent dans une dead letter queue que personne ne regarde. Un angle mort par construction.

03 · Le diagnostic

Extraire, pas échantillonner

Extraction systématique de l'historique via l'API Make, sur tout le parc. Les 5 376 échecs sont recensés un par un, pas estimés, puis classés par domaine : un geste commercial perdu n'a pas le même coût qu'une alerte manquée.

Un diagnostic partiel aurait produit une priorisation partielle. Le périmètre complet est ce qui rend l'arbitrage défendable.

04 · Le chiffrage

Chiffrer le risque en euros

Les échecs porteurs d'un enjeu financier sont valorisés ligne à ligne. C'est ce chiffre, pas le nombre d'échecs, qui permet d'arbitrer les reprises avec le métier.

05 · L'action

Prioriser, rejouer, refermer

Reprises ordonnées par impact décroissant, rejouées dans le parc corrigé. Le même mécanisme d'extraction sert ensuite de surveillance : la file d'échecs ne redevient jamais un angle mort.
