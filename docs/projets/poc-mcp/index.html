NODE : PROJET [06]

POC MCP — interroger le datawarehouse en langage naturel

Un serveur MCP (Model Context Protocol) place le LLM face à Snowflake avec des outils typés et un périmètre contrôlé. Le référentiel de documentation du datawarehouse — construit à la main — devient le contexte qui rend le modèle fiable sur un entrepôt réel.

ARCHITECTURE : LLM ↔ MCP ↔ SNOWFLAKE

Trois couches, deux frontières contrôlées

entrée utilisateur traitement garde-fou explicite sortie — pointillés : référentiels et contraintes
NODE : CE QUI REND LE POC FIABLE

La documentation d'hier est le garde-fou d'aujourd'hui

principe_01

Le référentiel comme contexte

Le LLM ne devine pas le schéma : il reçoit le référentiel technique construit lors de la documentation du datawarehouse — 24 schémas cartographiés, le lineage d'environ 65 vues, les pièges connus. C'est ce contexte structuré qui fait la différence entre une démo et un outil.

principe_02

Des outils typés, pas un accès brut

Le serveur MCP n'expose pas une connexion SQL : il expose trois outils à périmètre étroit — lister les schémas, décrire une vue, exécuter une requête SELECT. Le modèle explore l'entrepôt par étapes observables, jamais en aveugle.

principe_03

Lecture seule, périmètre fermé

Le rôle Snowflake utilisé par le serveur est en lecture seule et limité aux schémas documentés. Même un prompt adverse ne peut ni écrire, ni sortir du périmètre : la contrainte est dans l'infrastructure, pas dans le prompt.

principe_04

Des réponses sourcées

Chaque réponse cite les vues interrogées et joint le SQL exécuté. Une équipe métier peut vérifier la source, un data engineer peut rejouer la requête : la confiance se construit sur l'auditabilité, pas sur l'autorité du modèle.
