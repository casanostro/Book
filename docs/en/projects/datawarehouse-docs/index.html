The declared was not the real. The gap was not a detail: it was the teams' daily life, where every question about an unknown view went back to the same person.

Part 1 · The warehouse

Map what exists, not what is declared

01 · The declared

Docs that don't tell the real

Three Snowflake databases, documentation covering only a fraction. Impossible to evolve or debug a data chain nobody has the full map of.

02 · Exploration

Ask the system itself

Systematic exploration via information_schema and GET_DDL. The system describes its own structure; you just have to know how to ask. 24 real schemas, six times the documented scope.

03 · Lineage

Rebuild the real dependencies

Parsing the views' DDL to reconstruct who depends on what: about 65 views, their real dependencies, not the assumed ones. The map becomes usable.

04 · The reference

An asset, not a chore

A 314-line technical reference, now the source of truth of the data chain. It breaks the dependency on individual knowledge: the map outlives whoever drew it.

Written first for humans, it turned out to be exactly what a model needs to query the warehouse without inventing tables.

Part 2 · The agent

Yesterday's map, today's AI guardrail

The direct extension: an MCP connector between an LLM and Snowflake. Teams ask questions in plain language, the model explores the schema, generates the query and answers with its sources. Read-only access, controlled schema scope.

The reference built in part 1 is not a side document: it is the structured context that stops the model from hallucinating tables. The 24 schemas and the views' lineage are exactly what an LLM needs to stay reliable on a real warehouse. From reverse-engineering to self-service, never giving the model more than read access.

An LLM wired to a warehouse you haven't mapped invents answers with confidence. The guardrail is not in the model; it is in the context you give it. Lesson from the case

The logical next step: the same guardrails, pushed all the way to a product.
