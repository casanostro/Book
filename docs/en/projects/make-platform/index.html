CASE 02In productionBlind spot cleared

159 flows, but how many reliable ones?

DomainBusiness automation
RoleAdministration, diagnosis
StackMake, API, Python
StatusRecovery plan delivered

159 scenarios in production, 6 business domains, and an API migration that broke thousands of executions without a sound. 159 automations does not mean 159 reliable ones.

Investigation

From failure queue to action plan

01 · The fleet

What runs every day

159 scenarios covering commercial gestures, quality alerts, the missing-items base and other daily flows. A living fleet, wired to several systems via webhooks and APIs.

02 · The break

An API migration, thousands of failures

An API compatibility break made executions fail without firing an alert. Failures piled up in a dead letter queue nobody watched. A blind spot by construction.

03 · The diagnosis

Extract, don't sample

Systematic extraction of the execution history via the Make API, across the whole fleet. The 5,376 failures are listed one by one, not estimated, then classed by domain: a lost commercial gesture does not cost the same as a missed alert.

A partial diagnosis would have produced a partial prioritisation. The full scope is what makes the trade-off defensible.

04 · The pricing

Price the risk in euros

Failures carrying a financial stake are valued line by line. That figure, not the number of failures, is what lets you arbitrate recoveries with the business.

05 · The action

Prioritise, replay, close

Recoveries ordered by descending impact, replayed in the fixed fleet. The same extraction mechanism then serves as monitoring: the failure queue never becomes a blind spot again.
