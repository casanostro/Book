CASE 01 Root cause confirmed Severity high

The KPI had been lying for months

DomainData quality
RoleInvestigation, root cause

A service KPI published every week, false for months, with no alert ever firing. The system said all was well. The data said otherwise.

0.53 % of the expected volume. Not a drift of a few percent; a collapse. The question left was why nobody had seen it.

Investigation

From symptom to root cause

01 · Symptom

A number that contradicts the field

The service indicator showed an abnormal value in weekly reporting. No alert, no error log. The first reflex was not to fix, but to quantify the gap.

02 · Trace

Walk the calculation, node by node

From the reporting view to the order simulation engine. Every hypothesis tested by a reproducible query: expected against generated, then the exact share of rows in anomaly.

The diagnosis holds because every number is replayable. Intuition would not have defended the result to management; a query does.

03 · Fallback

The silent fallback

83 to 85 % of simulated rows never went through the nominal path. They fell back on a backup table, with no alert and no trace. The fallback had become the main road.

04 · Root cause

A table frozen since 2022

The backup table had not been fed since July 2022: about 3.6 million frozen historical rows. The engine drew stale data from it, believing it was doing its job.

The frozen table is an error. The fallback with no alert or log is the real design flaw. A silent fallback is a debt paid in trust.

05 · Fix

Repair the source and the silence

The proposed fix addresses both levels: re-activate the fed source, and make any future fallback loud. Impact quantified, cause documented, diagnosis reproducible.
